## 是什么

默认情况下，剧情模型写完正文后自己写 `<VariableThink>` 和指令块。开启分步更新后：

1. 剧情模型只写剧情，看不到变量更新规则；
2. 回复完成后，ERA 在后台另请求一次模型（可以是另一个接口、另一个模型），让它只根据这段剧情写指令；
3. 指令先试算一遍，有问题就把问题发回去让它重写；
4. 结果写到**那一楼**正文末尾的 `<era_extra>` 里，再按普通指令计算。

因为结果仍在正文里，滑动、删除、编辑、完全重算、导出聊天都和以前一样。

## 怎么开

悬浮球 → 面板 →“分步更新”，改完点“保存”：

| 设置 | 说明 |
| --- | --- |
| 变量更新方式 | “额外模型解析（剧情写完后另请求一次）”：开启；“随 AI 输出”：剧情模型自己写指令；“跟随角色卡”（默认）：按角色卡的推荐，卡片没有推荐时等同于随 AI 输出，见[角色卡推荐设置](#角色卡推荐设置) |
| 等待方式 | “后台更新，发送下一条前等它完成”（默认）：可以先看剧情，发送下一条时如果还没更新完会等它；“后台更新，不等待”：发送时不等 |
| 输出有问题时 | “保留有效的指令”（默认）：能用的指令照常生效；“整次放弃，变量不变”：只要有问题，这次输出全部不用 |
| 发送最近几楼 | 发给更新模型的剧情楼数，默认 2（玩家的一句和 AI 的一段） |
| 出错时重试次数 | 默认 1，最多 10。见[失败、重试与备用接口](#失败重试与备用接口) |
| 超时（秒） | 一次请求超过这个时间没有完成就算失败（可以重试），默认 120，最少 5 |
| 最大回复 token | 更新模型的最大回复长度，0 为不限（默认） |
| 温度 | -1 为不设置（默认），使用接口自己的温度 |
| 附加要求 | 附在发给更新模型的提示词最后，可以留空；可以使用 `{{ERA:路径}}` 宏 |
| EJS 预处理 | “自动”（默认）：装有提示词模板扩展时，按目标楼的状态渲染条目里的 EJS；“关闭”：ERA 不渲染，原文交给酒馆发送（扩展开启时，扩展会按最新状态渲染，写函数照常执行）。见 [EJS 预处理](#ejs-预处理) |
| 默认接口 | 来源可选“跟随酒馆当前连接”“酒馆的代理预设”“自定义接口”，并可指定模型。推荐前两种，见[API 密钥的安全](#api-密钥的安全) |
| 分组接口 | 输入分组名，点“为分组指定接口”，为 `[era_update:组名]` 分组单独指定接口；没有指定的分组用默认接口 |
| 备用接口 | 可以留空。主接口（分组接口或默认接口）请求失败时依次换用 |

设置保存在本机酒馆的全局变量里，**不会随角色卡导出**，对所有 ERA 卡生效。用“自定义接口”时密钥也存在这里，请先看[API 密钥的安全](#api-密钥的安全)。

“分步更新”页的“重新解析最后一条 AI 消息”可以为最后一条 AI 消息重新生成，替换上一次的结果。没有开启分步更新时也能用：消息里原有的指令保持不变，模型只补充遗漏的部分。

旧卡建议先点一次“工具”页的“更新旧卡的规则”。不更新也能用，只是更新模型不会使用 `<VariablePatch>`。

## 角色卡推荐设置

专门为分步更新写的卡（剧情条目不要求写指令、规则全在 `[era_update]` 条目里），可以在**角色卡变量**里推荐设置。角色卡变量随卡导出，玩家导入后不用自己去面板里开。

在酒馆助手的“变量管理器”→“角色卡”中添加 `ERA分步更新`，或在卡片脚本里写：

```javascript
await updateVariablesWith(variables => _.set(variables, 'ERA分步更新', {
  变量更新方式: '额外模型解析',
  聊天楼层数: 3,
  重试次数: 2,
}), { type: 'character' });
```

- 可以推荐的项：`变量更新方式`（`'额外模型解析'` 或 `'随AI输出'`）、`等待方式`、`失败处理`、`聊天楼层数`、`重试次数`、`超时秒数`、`最大回复`、`温度`、`附加要求`、`EJS预处理`（`'自动'` 或 `'关闭'`）、`正文前规划`（`'关闭'` 或 `'开启'`）、`更新模型预设` 与 `规划模型预设`（只能是 `'不使用预设'` 或 `'使用当前预设'`）、`附带角色信息`（`'关闭'` 或 `'开启'`），写法与面板中的值相同；没写的项用玩家自己的设置。
- **接口和密钥不能推荐**，始终用玩家自己的设置（默认是跟随酒馆当前连接）。头部提示词、请求方式、分组预设和具体的预设名也不能推荐，见[请求的组成](#请求的组成)。
- 不用手写：在面板“分步更新”页把设置调好，点“存为本卡推荐”（再点一次确认），就把上面这些可以推荐的项按当前的值写进这张卡的 `ERA分步更新`，覆盖原有的推荐；“清除本卡推荐”删除它。“变量更新方式”是“跟随角色卡”时不改这一项：卡里原来推荐了变量更新方式就保留原值，没有就不写。点第一次后，按钮旁会列出将写入的项。
- 只有玩家的“变量更新方式”是“跟随角色卡”（默认）时才采用；玩家选了“额外模型解析”或“随 AI 输出”，就完全按玩家的设置，卡片的推荐不起作用。
- 无效的值（例如写成字符串的数字、超出范围）会被忽略。
- 以前保存过设置的玩家，“变量更新方式”保持原来的选择，要采用卡片推荐需要改成“跟随角色卡”。

## API 密钥的安全

推荐把接口来源设为“跟随酒馆当前连接”或“酒馆的代理预设”。这两种方式下 ERA 不保存任何密钥：

- **跟随酒馆当前连接**：用酒馆正在使用的连接，密钥在酒馆自己的设置里。
- **酒馆的代理预设**：在酒馆的“API 连接”面板里填好反向代理地址和密码，保存为代理预设，这里只选预设名。还没有代理预设时，面板会提示怎么建。

“自定义接口”的密钥以明文保存在酒馆的**全局变量** `ERA额外模型` 里。全局变量不会随角色卡导出，但**所有酒馆助手脚本和角色卡的前端界面都能读取它**，包括你从别处下载的角色卡。

- 使用来路不明的角色卡（尤其是带脚本的卡）时，不要在这里填密钥。
- 换个地方存也不会更安全：酒馆助手脚本和前端界面与酒馆在同一个页面里运行，浏览器的 localStorage 它们照样能读，只是密钥不进酒馆的服务器设置和备份；脚本变量还会随卡导出。
- 面板“分步更新”页的“复制设置”复制的是去掉密钥的设置，密钥显示为“（已隐藏）”，可以直接贴给别人求助。
- ERA 自己不会把密钥写进聊天、日志或 `Era.extra.status()` 的记录里。

## 失败、重试与备用接口

每个分组单独请求、单独重试：

- **输出有问题**（指令不能生效、没有闭合、没有任何指令）：立即带着问题重试，最多“重试次数”次。
- **请求失败**：超时、限流（429）、服务器错误（5xx）、网络错误（例如连不上代理）会等一会儿再试（2 秒、4 秒、8 秒……最多 30 秒），同样占用重试次数；鉴权、参数等其他 4xx 错误（例如 401 密钥错误、400 参数错误）重试也不会成功，不再重试。
  - ：通过自定义接口或代理预设请求时，酒馆助手的 `generateRaw` 遇到 4xx、5xx 只抛出状态文字（例如 `Unauthorized`、`Bad Request`），没有状态码。ERA 按这些状态文字识别错误种类：填错密钥时不再按“重试次数”退避重试（有备用接口时仍会换用备用接口）。
- **备用接口**：填了备用接口时，主接口请求失败（不论什么错误）就立即换用下一个，不占重试次数；备用接口用完后，在最后一个上按上面的规则重试。输出有问题时不换接口。

重试仍不成功时弹出“变量更新失败”，可以在面板里重新解析。要看实际发送的提示词和模型的原始回复，可以在控制台执行 `Era.extra.status().last`（最近一次分步更新），面板“分步更新”页也会显示。最近 10 次分步更新与正文前规划的记录在 `Era.extra.status().history` 里（最新的在前，每条有时间、类型、楼层 MK、状态、提示词、原始回复、问题与告警），面板“分步更新”页的“请求记录”可以逐条展开。这些记录只在内存中，切换聊天时清空，不含密钥。

**告警**：条目过滤器出错、EJS 渲染出错或超时、模板调用了写函数、取不到目标楼之前的状态等情况，不影响这次解析的结果，记在 `warnings` 里，不算进 `problems`。在 `Era.extra.status().last.warnings`、`Era.extra.run()` 的返回值和 `era:extraStatus` 事件里都能看到，面板显示为“告警（n，不影响结果）”。条目没有按预期发给更新模型时，先看这里。

**写入已到正文、但同步还没算完**：更新模型的输出已经写进那一楼的正文，但 ERA 的同步队列很忙，在写入时限内没有算完。这种情况不算失败，下一次同步会按正文算出同样的结果。在它算完之前：

- `Era.extra.status().pendingSync` 列出这些楼的 MK，面板显示“已写入、等待同步算完”；
- “发送下一条前等它完成”和 `Era.extra.wait()` 会继续等它算完，不会让下一次生成拿到旧变量；放弃等待后不再拦之后的发送。

## 请求的组成

更新模型和规划模型的请求由 ERA 自己组织，默认不经过酒馆的预设，只发 ERA 的规则、`[era_update]`（或 `[era_plan]`）条目、变量和最近几楼的剧情。下面几项设置在面板“分步更新”页，默认都保持这个行为；它们对分步更新和正文前规划都起作用。发出的提示词从前到后是：

1. 头部提示词（填了才有）；
2. 预设中排在“聊天记录”之前的条目（选了使用预设才有）；
3. ERA 自己的提示词：说明、条目、角色信息（开启了才有）、变量、剧情，与不用这些设置时完全相同；
4. 预设中排在“聊天记录”之后的条目（选了使用预设才有）。

| 设置 | 默认 | 作用 | 角色卡能否推荐 |
| --- | --- | --- | --- |
| 更新模型预设 | 不使用预设 | 更新模型用不用酒馆的预设：`不使用预设`、`使用当前预设`、`使用指定预设`（再选一个预设）。可以为分组单独指定（“为分组指定预设”），没有单独指定的分组按这一项 | 只能推荐 `不使用预设` 或 `使用当前预设` |
| 规划模型预设 | 不使用预设 | 同上，用于正文前规划 | 同上 |
| 附带角色信息 | 关闭 | 开启后，在条目后面附上角色描述和用户人设（酒馆的 `{{description}}`、`{{persona}}`）；某一项为空时不加 | 可以 |
| 头部提示词 | 空 | 放在最前面的一条系统提示词，例如破限；为空时不加。可以用酒馆的宏（如 `{{char}}`） | 不能，只存在玩家本机 |
| 请求方式 | 非流式 | `流式` 时以流式请求（酒馆助手 `generateRaw` 的 `should_stream`），有的接口只支持流式时用它；结果一样是整段处理 | 不能 |

**使用预设时**：预设里启用的、有内容的条目（占位符条目如“聊天记录”“角色描述”“世界书”除外），保留各自的角色，按预设里的顺序发送：排在“聊天记录”之前的放在 ERA 的提示词前面，排在“聊天记录”之后的（常见的是末尾的破限和输出要求）放在 ERA 的提示词后面；预设的温度、top_p、top_k、频率惩罚、存在惩罚和最大回复长度也一并使用。面板里填了“温度”或“最大回复”时，以面板为准。“使用当前预设”用的是酒馆正在用的预设，包括还没保存的修改。

- 预设里给剧情模型写的要求（字数、文风、“输出正文”等）也会发给更新模型。ERA 的说明在后面并且要求只输出指令，但模型不一定都听；更新模型输出不稳定时，先换回“不使用预设”试试。
- 预设绑定的正则、酒馆助手脚本不起作用。按聊天深度插入（in_chat）的条目不按深度插入，按它在预设列表里相对“聊天记录”的位置放在 ERA 提示词的前面或后面：例如深度 0 的输出要求如果在列表里排在“聊天记录”之前，会放在最前面，而不是像酒馆里那样在最末尾。
- 预设不存在、读取失败、选了“使用指定预设”却没选预设时，这一次不使用预设照常请求，原因记在告警（`warnings`）里。
- 预设只存在玩家本机，所以角色卡只能推荐“不使用预设”或“使用当前预设”，不能推荐具体的预设名；卡片写了 `使用指定预设` 会被忽略。

## 世界书条目怎么写

按条目**名字**区分：

| 名字中含有 | 剧情模型 | 更新模型 |
| --- | --- | --- |
| （什么都没有） | 能看到 | 看不到 |
| `[era_update]` | 看不到 | 能看到 |
| `[era_update:组名]` | 看不到 | 只有这一组能看到 |
| `[era_both]` | 能看到 | 能看到 |

- “ERA 变量操作规则”“ERA 变量意图说明”和“ERA 表达式规则”等同于 `[era_update]`，旧卡不用改名。名字必须一字不差（中间有一个空格），否则会被当成普通条目发给剧情模型。
- **只有更新模型应该写指令。** 其他世界书条目或预设里如果也要求剧情模型输出变量指令（例如“输出格式”条目末尾的指令要求），剧情模型仍会自己写指令，ERA 就不会再请求更新模型：
  - 世界书条目：把这一段拆成单独的条目，名字加 `[era_update]`；
  - 预设：预设条目不能加标记，请从预设中删掉这一段，移到带 `[era_update]` 的世界书条目里。
- 没有开启分步更新时，这些标记不起作用，条目照常发送，所以同一张卡两种方式都能用。
- 读取全局、角色卡（群聊时为全部成员）、聊天和用户人设绑定的世界书。
- 蓝灯条目总是发送；绿灯条目按关键字匹配最近几楼。递归、概率、分组权重等世界书功能对更新模型无效。条目开头的 `@@activate`（不看关键字）、`@@dont_activate`（不发送）照常生效，`@@` 开头的装饰器行不会发给更新模型。
- 条目可以按目标楼的状态动态选择：用条目过滤器或 EJS，见[下一节](#按目标楼的状态选择条目)。
- 条目里可以使用 `{{ERA:路径}}`，取的是这一楼在没有额外模型输出时的值（已含这一楼自己的指令和脚本写入）。没有任何条目写 `{{ERA:$ALLDATA}}`（或 `{{ERA-withmeta:$ALLDATA}}`）时，会自动附上全部变量。
- 注册了变量结构（`Era.registerSchema`）时，没有任何条目写 `{{ERA-schema}}` 就会自动附上结构说明；写了就按你安排的位置放。快速初始化生成的“ERA 变量意图说明”已经包含这两个宏，不会重复发送。
- `{{ERA-issues}}`在发给更新模型的提示词里展开为空：它报告的是剧情模型上一条回复的问题，更新模型有自己的重试。

发给更新模型的其他内容：

- 聊天记录去掉指令块和思考块，并应用酒馆的提示词正则；AI 消息里的状态栏占位符（`特殊符号值`）也会去掉，规则与发给剧情模型时相同（自定义的符号只在开启“在ai消息尾部生成特殊符号”时处理），没点过“更新旧卡的规则”的旧卡也一样。
- 提示词里“这一楼已经执行的更新”只列出真正执行了的指令：新建的聊天里，思考块中的指令、设置了“指令外层标签”时外层标签之外的指令都不算。

更新模型的输出：

- 输出里思考块中的指令不算。思考标签取脚本设置“思考标签”，并且总是包括 `think`、`thinking`。
- 输出写进 `<era_extra>`，不受“指令外层标签”限制：开启了外层标签的聊天里，分步更新的结果照常生效，试算、重试和“整次放弃”也照常进行。

## 按目标楼的状态选择条目

。更新模型解析的是**某一楼**（目标楼），条目应当按那一楼的状态选择，而不是按最新状态或世界书文件里当前的开关。例如卡里有和平、战争两个时代的两套规则：重新解析战争爆发之前的楼，应当拿到和平时代的规则。

用脚本在发送时改写世界书开关（例如 `replaceWorldbook` 写回 `enabled`）的卡，开关反映的是“上次发送时”的状态。重新解析旧楼、切换聊天或删楼之后，分步更新会按这个开关选错条目。ERA 提供两种按目标楼状态选择的方式，都只作用于发给更新模型的条目：

| 方式 | 适合 | 依赖 |
| --- | --- | --- |
| 条目过滤器 `Era.registerEntryFilter` | 习惯写脚本的作者；原来用脚本改写世界书开关的卡 | 无 |
| EJS（`@@if`、`<% %>`） | 已经用 EJS 写动态条目的卡 | 提示词模板扩展 |

**目标楼的状态**是这一楼在没有额外模型输出时的状态（已含这一楼自己的指令和脚本写入），与条目里 `{{ERA:路径}}` 取的值相同。所以更新模型在这一楼才写入的值（例如这一楼才把“世界.时代”改成“战争”），这一楼的选择看不到，下一楼才看得到。之前的楼层还没同步完，或者开启了日志折叠又没有存档、算不出这一楼之前的状态时，退回用最新状态，并记一条告警。

### 处理顺序

对名字含 `[era_update]`、`[era_both]` 的条目（以及上面三条内置规则条目），依次：

1. **条目过滤器**：任一过滤器返回 `false` 就不发送；返回 `true` 或字符串就纳入（即使文件里关闭了、关键字没有匹配）；都不表态时进入下一步。
2. **文件里的设置**：开关、`@@dont_activate`、`@@activate`、蓝灯或绿灯关键字。
3. **`@@if`**（EJS 预处理）：条件不成立或求值出错时不发送。
4. **渲染 EJS**：酒馆宏（`{{user}}`、`{{// }}` 等）先于 EJS 替换。
5. 内容为空的条目去掉。
6. 替换 ERA 宏。是否自动附上全部变量和结构说明、是否允许 `<VariablePatch>`，都按这时的条目内容判断。

过滤器返回 `true` 时只跳过第 2 步，`@@if` 和 EJS 照常处理。返回字符串时用它替换条目内容，跳过第 2 到 4 步，酒馆宏和 ERA 宏照常替换。返回的字符串里不要写 EJS：ERA 不渲染它，提示词模板扩展开启时会在发送前按最新状态渲染。

### 条目过滤器

```typescript
Era.registerEntryFilter(name: string, filter: (entry, ctx) => boolean | string | void): () => void
Era.hasEntryFilter(name: string): boolean
```

在角色卡脚本里注册。分步更新收集条目时，对每个候选条目调用一次过滤器。正文前规划和主生成（玩家触发的剧情生成加载世界书时）也调用它，用 `ctx.purpose` 区分；主生成里纳入的条目仍受酒馆的延迟、分组和预算限制，带粘性或冷却的条目只能排除，详见 [08-动态提示词.md](08-动态提示词.md)；按变量切换条目的整体做法见 [08-动态提示词.md](08-动态提示词.md)。

| 返回值 | 含义 |
| --- | --- |
| `false` | 不发送这个条目 |
| `true` | 纳入，即使文件里关闭了、关键字没有匹配 |
| 字符串 | 纳入，并用这段文字替换条目内容；后面的过滤器看到的是替换后的内容。替换成空白文字等于不发送 |
| 其他（`undefined` 等） | 不表态，按文件里的开关和关键字 |

`entry` 是条目的副本：`world`（所在世界书）、`uid`、`name`、`content`、`enabled`（文件里的开关）等。`ctx`：

| 字段 | 内容 |
| --- | --- |
| `stat` | 目标楼的状态，去掉了 `$` 开头的字段，已反转义 |
| `statRaw` | 目标楼的原始状态（转义过的，含 `$meta` 等字段） |
| `text` | 匹配关键字用的文本：到目标楼为止的最近几楼正文，楼数同“发送最近几楼” |
| `mk` | 目标楼的 MK |
| `purpose` | `'extra'`（分步更新）；还有 `'plan'`（正文前规划）、`'main'`（主生成，`stat` 是最新的变量） |

要求：

- **同步的纯函数**，只依赖 `entry` 和 `ctx`。`ctx` 是只读的，不要修改。重新解析时同一楼会再算一遍，结果应当相同。
- 返回 Promise、抛出异常时忽略这个过滤器的结果（按不表态处理），并记一条告警。
- 在重入保护下运行：执行期间调用 `Era.commit`、`Era.applyText`、`Era.extra.run` / `wait` 或发出写入事件，这个过滤器的结果会被忽略，并记一条告警。
- 同名的过滤器会被替换；有多个过滤器时按名字顺序调用。返回值是注销函数。
- 和钩子一样只存在于内存中，属于注册它的角色卡；换卡后遗留的过滤器会被自动注销。名字无效或参数不是函数时弹窗提示、不注册，可以用 `hasEntryFilter(name)` 确认。

示例：和平、战争两套规则二选一。两套规则条目都写成更新条目，名字分别带 `[和平]`、`[战争]`：

```javascript
// 角色卡脚本
await waitGlobalInitialized('Era');
const unregister = Era.registerEntryFilter('我的卡.规则二选一', (entry, ctx) => {
  if (entry.name.includes('[和平]')) return ctx.stat.世界?.时代 !== '战争';
  if (entry.name.includes('[战争]')) return ctx.stat.世界?.时代 === '战争';
  // 其他条目不表态，按文件里的开关和关键字
});
$(window).on('pagehide', unregister);
```

使用 `util/era.ts` 的前端项目可以改用 `registerEraEntryFilter(name, filter)`：ERA 加载得比脚本晚时会等待，ERA 脚本重载后自动补注册，脚本卸载时自动注销；旧版 ERA 没有这个功能时只在控制台提示，卡照常运行。

过滤器也作用于主生成，同一个函数让剧情模型和更新模型拿到同一套条目，原来在发送时改写世界书开关的脚本可以去掉，迁移步骤见 [08-动态提示词.md](08-动态提示词.md#从脚本改写世界书开关迁移)。只想影响分步更新的过滤器，对 `ctx.purpose` 不是 `'extra'` 的调用返回 `undefined`。

### EJS 预处理

设置“EJS 预处理”为“自动”（默认），并且装有、开启了提示词模板扩展（扩展的总开关和“处理生成内容”都开着）时，ERA 按目标楼的状态处理发给更新模型的条目：

- `@@if 条件`：条件按目标楼的状态求值，不成立或出错时不发送；
- `<% %>`、`<%= %>`、`<%- %>`：渲染后发送。渲染结果为空时不发送；出错或超时时不发送（不会把 JS 源码原样发给更新模型），并记一条告警；
- `@@private` 照常生效。

模板里能用的变量：

- `getvar('stat_data.路径')`，以及 `getLocalVar`、`getGlobalVar`、`getMessageVar`，不论 `scope` 是什么，只要键以 `stat_data` 开头，读的都是**目标楼**的状态；模板里直接访问的 `variables.stat_data` 也一样。读到的是转义过的原始数据（含 `$meta` 等字段），与剧情模型那边扩展读到的格式相同。
- 其他键照常读取。
- `era.purpose` 为 `'extra'`、`era.mk` 为目标楼的 MK，模板可以据此判断自己是在更新模型流程里渲染。

在更新模型流程里不执行的操作：

- 写变量（`setvar`、`incvar`、`decvar`、`delvar`、`insvar` 及其 Local、Global、Message 版本，`patchVariables`、`setVariableSchema`）、激活世界书（`activewi`、`activateWorldInfo` 等）、`injectPrompt`、`activateRegex`、`execute`：换成空操作，并记一条告警。`[era_both]` 条目在剧情模型那边已经渲染过一次，再执行会让副作用发生两次。
- `define` 只在这次渲染里有效，不写进扩展的全局定义。同一次解析的条目按 order 依次渲染，共用一个环境。
- 扩展的特殊条目不发给更新模型：名字含 `[GENERATE:`、`[RENDER:`、`@INJECT`、`[InitialVariables]`，或带 `@@generate_*`、`@@render_*`、`@@iframe`、`@@message_formatting`、`@@preprocessing`、`@@only_preload`、`@@initial_variables` 的条目。

一次解析的全部条目共用 15 秒渲染时限，只渲染一次，各分组和重试共用渲染结果；发送前等待的时限也计入这 15 秒。

设为“关闭”，或者没有装、没有开启扩展（总开关或“处理生成内容”关着）时：`@@if` 不求值，条目照常发送；`<% %>` 由 ERA 原样交出，条目开头的 `@@` 装饰器行不发送。扩展开启但设为“关闭”时，扩展会在发送前按**最新状态**渲染这些 `<% %>`，写函数也会执行，所以装着扩展时不要设为“关闭”。

**剧情模型那边的 EJS**（主生成）由提示词模板扩展自己渲染，ERA 不参与。只用 EJS、不用 ERA 宏的卡，在滑动（swipe）重新生成时，EJS 可能读到回滚前的状态：扩展读取变量时，ERA 还没把这一楼回滚算完。提示词里只要有一个 ERA 宏（例如某个条目里的 `{{ERA:路径}}`），ERA 就会先等同步算完（最多约 3 秒）再替换宏；使用聊天补全（Chat Completion）类接口时，扩展在这之后渲染，读到的是滑动后的状态。文本补全类接口上，扩展先于 ERA 渲染，这个办法不保证有效。

## 正文前规划

分步更新在正文**之后**结算变量。检定、骰点也放在正文之后时，容易出现“正文写着打赢了，数值却没过检定”。正文前规划把这类结果挪到正文**之前**：

1. 玩家点击发送时，ERA 先等上一楼的分步更新完成，再请求规划模型。
2. 规划模型读 `[era_plan]` 条目（规划规则）、当前变量、最近几楼剧情和玩家这一轮的行动，结算需要先确定的结果，输出一句摘要和指令块。需要随机结果时，它使用 ERA 预先掷好的骰子（`d20`、`d100`、`3d6`），而不是自己编。
3. ERA 按玩家消息的规则试算这些指令（不执行钩子和工具），有问题时带着问题重试，和分步更新一样。
4. 结果追加在玩家消息末尾，再替玩家发送：

```xml
我挥剑砍向哥布林
<era_plan>
<PlanSummary>攻击命中，哥布林受到 7 点伤害，剩余 3 点生命</PlanSummary>
<VariableEdit>{"敌人": {"哥布林": {"生命": 3}}}</VariableEdit>
</era_plan>
```

5. 玩家消息里的指令在发送时就执行；`<era_plan>` 被数据隐藏正则从显示和提示词里去掉。生成前，ERA 把摘要注入提示词（深度 0，系统角色），并说明“结果已经计入变量，正文按这个结果写，不要再输出对应的指令”。分步更新的更新模型看到的也是这句摘要。

规划写在**玩家楼**里，正文就是事实来源：滑动、重新生成 AI 回复时复用同一个规划，骰点不会重掷；删除玩家消息时规划一起撤销。

**怎么用**：

- 在世界书里建规划规则条目，名字带 `[era_plan]`，写清什么行动需要检定、怎么判定、改哪些变量。这些条目只发给规划模型，剧情模型和更新模型都看不到；两边都要看的设定用 `[era_both]`。ERA 自己的规则条目（`ERA 变量操作规则` 等）也会发给规划模型。
- 在 ERA 面板“分步更新”页把 **正文前规划** 设为“开启”，或在角色卡变量 `ERA分步更新` 里推荐 `正文前规划: '开启'`。规划模型使用这一页的接口设置（可以给分组名 `plan` 单独指定接口）、重试次数、超时、附加要求；`变量更新方式` 不需要是“额外模型解析”。
- 卡里没有 `[era_plan]` 条目时不规划。群聊、空消息、斜杠命令不规划；快速回复和脚本触发的生成不经过发送按钮，也不规划，它们可以先调用 `Era.extra.plan(text)` 拿到规划后的文字再发送。
- 规划模型认为这一轮不需要结算时（只输出 `<VariableThink>无需规划</VariableThink>`），照原样发送。
- 规划失败（接口出错、输出一直有问题）时**不发送**，文字留在输入框里，并弹窗说明原因；再点一次发送就跳过规划直接发送。
- 规划结果不满意：面板“分步更新”页的“重新规划最新的玩家消息”（或 `Era.extra.replan()`）重新结算并替换 `<era_plan>`，之后重新生成 AI 回复。

**限制**：规划发生在玩家消息有 MK 之前，所以规划里不能用 `$expr` 和工具调用（它们的随机数依赖 MK），只接受写出结果的 `<VariableInsert>`、`<VariableEdit>`、`<VariableDelete>`。旧卡需要先在面板点“更新旧卡的规则”，让数据隐藏正则认识 `<era_plan>`，否则规划块会显示在聊天里。

## 分组

变量很多时，可以用 `[era_update:战斗]`、`[era_update:好感]` 把规则分成几组。各组同时请求，还可以在面板里为每组指定不同的接口。没有组名的 `[era_update]` 条目每组都会看到。

各组应当负责互不重叠的变量；如果改了同一个变量，按组名顺序执行。

## 在自己的前端界面里发送

“发送下一条前等它完成”只拦得住酒馆自己的发送按钮和回车。前端界面、快速回复用 `/send`、`/trigger` 等命令发送时不会等待，这时更新仍会在后台完成并写到正确的楼层，只是紧接着的那次生成看到的还是更新前的变量。需要等待的前端界面或脚本，在发送前加一行 `await Era.extra.wait()`：

```javascript
await Era.extra.wait(); // 没有正在进行的更新时立即完成；返回 false 表示没等到完成
await triggerSlash('/send 你好 | /trigger');
```

## 什么时候不会请求

- 没有任何发给更新模型的条目（按[按目标楼的状态选择条目](#按目标楼的状态选择条目)筛选、渲染之后）；
- 剧情模型自己已经写了指令（新建的聊天里，思考块中的指令、设置了“指令外层标签”时外层标签之外的指令不算）；
- 开场白、脚本创建的消息。

请求期间重新生成、继续、删除该楼或切换聊天，结果会作废，不会写到别处（继续写完后会重新解析）；只是滑到别的 swipe 看看，结果仍会写到原来那一条。

## 发送前等待

选了“发送下一条前等它完成”时，点发送会先等更新完成，再替你点一次发送：

- 最多等到每次请求都超时、用完全部重试和备用接口、再加上渲染条目和写入的时间（默认设置下约 8 分半）；一般远早于此就完成了。
- 输出已经写进正文、同步还在排队时，也会等它算完（见[失败、重试与备用接口](#失败重试与备用接口)）。
- 等待期间会显示“正在等待变量更新完成”，**点击这条提示**可以不再等待，直接发送。
- 没等到完成就发送时，会提示“变量仍在更新，已先发送”：更新完成后仍会写回原来那一楼，只是这次生成看到的是更新前的变量。
- 等待期间再次点发送不会重复发送；等待期间切换聊天、改了文字或开始了别的生成，就不再自动发送，文字留在输入框里。
